# Android audio diagnostic (versionCode 3)

This is an asset-free diagnostic APK, not a playable Lost Odyssey runtime. Install it over the Phase 1 probe. It uses the same package ID and debug signing key, preserving private files and the Share log flow.

## Phone test

1. Turn media volume up to a comfortable level and launch **Lost Odyssey Audio Test**.
2. Listen for a quiet 750 ms stereo tone (440 Hz left / 660 Hz right).
3. Wait for the result dialog, tap **Share log**, and attach it to the conversation.
4. Report whether you heard the tone and whether audio was routed to phone speakers, headphones, or Bluetooth.

The result dialog reports guest-memory alias coherence, Vulkan swapchain creation, XMA decoder API smoke checks, and PCM queue consumption. Queue consumption alone cannot prove speaker audibility. No microphone, network, game import, or game asset is needed.

The XMA check uses the real pinned Xenia FFmpeg decoder, matching production `apu/xma.cpp`: mono/stereo at 24/32/44.1/48 kHz, decoder creation/open, send/receive of an intentionally invalid two-byte packet, error validation, flush, and cleanup. FFmpeg's "XMA Frame is to small, 2 bytes" log lines are expected for this negative test. Valid game-frame decoding and sound quality are not tested.

## Implementation and validation

- Added Android ARM64 `config.h` generated by the pinned fork's configure using NDK r27d, Android API 28, cross compilation and PIC; retained NEON assembly.
- Fixed FFmpeg config lookup to use the include file's directory rather than the caller's source directory. Existing desktop include behavior remains equivalent.
- Embedded static FFmpeg libraries use hidden C symbols and PIC on Android, allowing NEON's direct references to internal DSP tables in a shared library. FFmpeg's native shared build similarly localizes internals with a version script.
- Probe uses SDL float32 stereo output, a low-amplitude faded synthetic tone, and a bounded three-second wait for queue consumption. It closes the audio device before results/sharing.
- ARM64 build and shared-library link succeeded. Java/DEX packaging, APK signing and 16 KiB ZIP alignment succeeded.
- The exact decoder smoke function also ran against the pinned fork's Linux decoder: all eight combinations passed; CTest passed. Android execution still requires the phone test.
- Existing guest-memory/Vulkan tests are retained; no full desktop runtime rebuild is claimed.

## Build

The committed Android configuration lets the normal probe build fetch the pinned FFmpeg source automatically:

```sh
python tools/build_android_probe.py --sdk /path/to/android-sdk --cmake cmake --ninja ninja
```

To regenerate the Android configuration from a clean pinned FFmpeg source:

```sh
python tools/configure_android_ffmpeg.py --source /path/to/pinned-xenia-ffmpeg --ndk /path/to/ndk/27.3.13750724
```

The script checks the source commit and generates in an isolated source copy because this fork's checked-in `config.h` prevents conventional out-of-tree configure. Original fetched sources are not edited. The helper requires a POSIX host with the pinned NDK. `FFMPEG_CONFIGURATION` retains the actual compiler path as build provenance; paths in that string are not used to compile the committed header.

To run the host decoder check without a game or runtime:

```sh
cmake -S . -B out/xma-smoke -DLO_BUILD_RUNTIME=OFF -DLO_BUILD_RECOMP_LIB=OFF -DLO_BUILD_XMA_DECODER_SMOKE=ON
cmake --build out/xma-smoke --target LoXmaDecoderSmoke
ctest --test-dir out/xma-smoke --output-on-failure
```

Use Clang on the supported desktop host. The generated config depends on FFmpeg commit `15ece0882e8d5875051ff5b73c5a8326f7cee9f5`.
